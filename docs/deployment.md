# Docker, перенос базы и автоматическая выкладка

Сервер и домен пока не выбраны. В репозитории подготовлены контейнеры, операции с базой и GitHub Actions; доставка на сервер выключена, пока repository variable `DEPLOY_ENABLED` не равна `true`. Добавление этих файлов само по себе не переносит и не меняет боевой сайт.

## Что хранится где

Код и публичные материалы хранятся в Git, готовый PHP-образ — в GHCR. Текущие данные MySQL/MariaDB хранятся в постоянном Docker volume. Пароли находятся на сервере в `.secrets/`, параметры — в `.env`. Эти файлы, SQL-архивы и `backups/` не коммитятся.

Реальная база содержит заявки, телефоны, платежи и учётные записи. Для её переноса нужен отдельный локальный архив; публичный GitHub-репозиторий для этого не используется. Исходный `data/seed.json` — наполнение новой базы, он не заменяет экспорт текущей. Экспорт актуальной боевой БД в рамках подготовки не выполнялся.

## Локальная проверка

Установите Docker Engine с плагином Compose либо Docker Desktop. Команды первоначальной настройки, создания новой базы и импорта находятся в [README](../README.md). Операции импорта выполняются явно; обычная выкладка существующие данные не заменяет.

Для проверки подготовленной инфраструктуры:

```bash
docker build --build-arg BUILD=local -t a-deti:local .
bash tests/deployment.sh
```

Тест использует отдельный проект Compose и временные параметры, проверяет приложение и операции переноса. Контейнеры повседневного локального проекта он не использует.

## Будущий сервер

Подходит Ubuntu с Docker Engine, Compose plugin, Bash, Python 3, curl, gzip и flock. Установка Docker описана в [официальной инструкции](https://docs.docker.com/engine/install/ubuntu/). Для первого выпуска подготовьте каталог, например `/opt/a-deti`, и отдельного пользователя доставки. У него должны быть права на этот каталог и Docker. Доступ к Docker фактически даёт административные права на сервер; такой SSH-ключ не используют для других задач.

При выборе домена направьте его DNS на сервер, откройте TCP 80/443 и настройте адрес сайта и email в `.env`. Профиль Compose `https` запускает Caddy, который получает и продлевает сертификат. База не публикуется наружу; локальный HTTP-порт приложения привязан к `127.0.0.1` и нужен для диагностики.

Первоначальная настройка создаёт `.env` и секреты, запускает базу и позволяет явно выбрать новую базу из seed либо импорт существующего архива. После этого создаётся новая учётная запись администратора. Публичного пароля по умолчанию нет. Архив до и после переноса храните отдельно от сервера и репозитория; проверьте восстановление до переключения домена.

## GitHub Actions

`CI` запускается для pull request и `main`: проверяет shell, JavaScript и PHP, собирает Docker-образ и выполняет интеграционный тест. `Release` реагирует только на успешный `CI` от push в `main`, берёт ровно проверенный SHA и публикует образ `ghcr.io/andreyshelemetev/a-deti:<SHA>`. Доставка использует digest `@sha256:…`, поэтому повторное назначение тега не подменит выбранный образ.

Внешние actions закреплены полными commit SHA из [actions/checkout](https://github.com/actions/checkout), [docker/setup-buildx-action](https://github.com/docker/setup-buildx-action), [docker/login-action](https://github.com/docker/login-action) и [docker/build-push-action](https://github.com/docker/build-push-action). Только job публикации получает `packages: write`; проверкам и доставке достаточно `contents: read`. Pull request не получает ключ доставки и не публикует образ.

GHCR-пакет при первой публикации может оказаться приватным. До включения доставки выберите один вариант: сделайте образ публичным в настройках пакета или заранее выполните `docker login ghcr.io` на сервере под пользователем доставки с отдельным токеном `read:packages`. Токен вводится через `--password-stdin`; его не записывают в Git или команды workflow.

Для включения доставки добавьте secrets репозитория либо environment `production`:

| Secret | Назначение |
| --- | --- |
| `SSH_HOST` | DNS-имя или IPv4 сервера |
| `SSH_USER` | Пользователь доставки |
| `SSH_PORT` | SSH-порт; если не задан, используется 22 |
| `SSH_PRIVATE_KEY` | Отдельный приватный ключ доставки |
| `SSH_KNOWN_HOSTS` | Проверенная запись ключа SSH-сервера, включая `[host]:port` для нестандартного порта |
| `DEPLOY_DIR` | Подготовленный абсолютный каталог, например `/opt/a-deti`, без пробелов |

Ключ сервера сверьте через консоль провайдера или другой доверенный канал. Workflow использует `StrictHostKeyChecking=yes` и не принимает новый ключ автоматически. При необходимости задайте reviewers у environment `production`.

После первоначальной настройки сервера и registry-доступа установите repository variable `DEPLOY_ENABLED=true`. Следующий успешный CI от push в `main` запустит доставку. Для текущего коммита можно повторить его исходный CI от push в `main`. Сборка старого коммита не выкладывается, если `main` уже ушла вперёд.

## Порядок обновления

Workflow передаёт только `compose.yaml`, `docker/Caddyfile` и `ops/*.sh`; `.env`, `.secrets/` и база остаются на сервере. Скрипт `ops/deploy.sh IMAGE SHA DEPLOY_DIR` берёт файловую блокировку и сохраняет предыдущую конфигурацию в `.deploy/`.

Затем он загружает образ и проверяет конфигурацию Caddy, ждёт готовности MariaDB и останавливает приложение на короткое окно обслуживания. До изменения схемы обязательна успешная резервная копия `backups/before-…sql.gz`. Новый образ выполняет `php bin/console.php migrate` отдельным контейнером; импорт и seed при этом не запускаются. Далее запускается приложение, проверяются состояние контейнера и `/healthz.php` с ожидаемым BUILD, после чего обновляется HTTPS-прокси и проверяется готовность его конфигурации. Успешный образ и BUILD записываются в `.release.env`, не переписывая пользовательский `.env`.

Если миграция, запуск или проверка не прошли, скрипт восстанавливает прежнюю конфигурацию и образ. Тома и данные он не удаляет. Ошибка остаётся ошибкой workflow даже после успешного отката, чтобы оператор увидел необходимость проверки.

Откат кода не отменяет миграцию БД. Изменения схемы должны оставаться совместимыми с предыдущим выпуском. Удаление колонок и другие несовместимые изменения требуют отдельного плана и окна обслуживания. SQL-архив не восстанавливается автоматически поверх действующей базы.

Не используйте `docker compose down -v` для обычного обновления: эта команда удаляет постоянные тома. Резервные копии нужно регулярно переносить за пределы сервера и проверять восстановление.
